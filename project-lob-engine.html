lob-engine: a matching engine built four times, and measured each time

A limit order book and matching engine in C++20. I started with the textbook design, profiled it, and rebuilt it until the hot path made no heap allocations — then checked every version against a brute-force reference over millions of random events.

The problem

A matching engine keeps every resting buy and sell order for an instrument and pairs incoming orders with them by price first, then arrival time. It has to do that correctly for every order type, and it has to do it in a predictable number of nanoseconds, because the slowest events are the ones that matter.

I wanted a project where both claims — “it is fast” and “it is correct” — were backed by something a reader could re-run.

What I built

The same rules, four data structures. Limit, market, IOC, FOK and post-only orders; cancel; modify with explicit queue-priority rules; self-trade prevention. Prices are integer ticks, and the book is a deterministic function of its input.

A profile that changed the plan. Replacing the tree with a flat array only bought 1.4×. Sampling showed why: 57% of the time was in malloc and free. Moving orders into a preallocated pool with index-linked queues and an open-addressing id table removed the allocator from the profile entirely and gave a further 4.5×.

A reference implementation and a differential test. A deliberately simple book — one unsorted vector, scanned for every decision — processes the same randomized stream as the fast books. Their output must match after every event. A libFuzzer target does the same with arbitrary bytes, and the suite runs under AddressSanitizer, UBSan and ThreadSanitizer.

A lock-free pipeline and a replay format. A single-producer single-consumer ring buffer with documented memory ordering connects feed, matcher and publisher threads. A compact binary log replays to the same output hash on every version, compiler and standard library I tried.

A research layer and a demo. A Python backtester drives the real engine over a pipe, so a market-making strategy gets true queue priority against synthetic order flow. The engine is also compiled to WebAssembly, so the demo page lets you submit orders into it in the browser.

Two results I did not expect

An optimization that made the benchmark slower, and stayed. A flat price array has one bad case: when the best level empties and the next one is far away, finding it took about 14 microseconds instead of about 12 nanoseconds. A two-level bitmap fixes that — the same input went from 0.12M to 153M events per second — but costs about 2% on ordinary workloads. I kept it on by default, because a matching engine should not have an input that makes it a thousand times slower.

The multi-threaded version is slower. Decoding, matching and encoding one message is about 18 ns of work. Passing it between cores twice costs more than that, so the three-thread pipeline runs at 22.6M messages per second against 54.4M on one thread. The write-up explains the mechanism and when the pipeline is still the right structure. I report it because it is what I measured.

What it does not do

One instrument, in memory, on a laptop without isolated cores. No network layer, persistence, auctions or exchange connectivity. All order flow is synthetic, and the strategy study is a model study, not a trading result. The repository's DESIGN.md lists the limitations and what I would build next.
